## Демонстрация за пять минут

1. Покажи три начальные задачи. Создай четвёртую через New task и объясни ограничения ввода.
2. Выбери Deadline first и бюджет 90 минут. Покажи, что ближайший дедлайн идёт первым, а последняя задача делится по оставшемуся времени.
3. Выбери Priority first. Сначала будет задача с приоритетом 3. Это замена объекта Strategy без переписывания алгоритма распределения бюджета.
4. Отметь сессию как выполненную. Открой Activity: событие одновременно обновляет интерфейс и журнал.
5. Выключи и включи Include progress summary. Покажи различие отчётов и экспорт в TXT.
6. Закрой и открой приложение: план и прогресс сохранены. Журнал событий относится только к текущему запуску.

## Шесть паттернов простыми словами

**Builder:** PlanBuilder постепенно получает имя, настройки и сессии. `build()` создаёт Plan с проверенными ограничениями. Список копируется, поэтому последующие изменения builder не меняют сохранённый план.

**Strategy:** интерфейс SchedulingStrategy и реализации DeadlineStrategy / PriorityStrategy. Facade получает стратегию параметром, вызывает order(), затем одинаково распределяет бюджет. Стратегия отвечает за порядок, а не за сохранение.

**Observer:** EventBus хранит подписчиков. ActivityLog записывает сообщения, подписчик StudyWindow обновляет таблицы. Событие отправляется после успешного save(). Иначе интерфейс мог бы показать несохранённые изменения.

**Adapter:** PropertiesRepository реализует доменный Repository, переводя Task/Plan/Session в ключи и значения java.util.Properties и обратно. Это именно адаптация двух интерфейсов, а не просто класс с названием Adapter.

**Decorator:** TextPlanReport и ProgressReportDecorator реализуют PlanReport. Декоратор хранит обёрнутый PlanReport, вызывает его render(), затем добавляет прогресс. Можно составлять декораторы через один интерфейс.

**Facade:** StudyFacade предоставляет интерфейсу операции saveTask, generate, toggleSession, deleteTask, deletePlan и report. Он координирует остальные компоненты; Swing не знает формат хранения.

## Вопросы, которые нужно уметь объяснить

- Почему данные неизменяемые? Чтобы изменения одного плана не затронули остальные и чтобы после ошибки записи можно было оставить прежнее состояние.
- Почему завершение сессии не завершает задачу? Сессия может покрывать только часть задачи. Вся задача завершается отдельно через Edit.
- Что будет после удаления задачи? Сохранённые планы сохраняют её текстовый снимок и taskId; они остаются историческим результатом.
- Что при ошибке записи? Временный файл удаляется, новый snapshot не становится текущим, событие успеха не публикуется.
- Где ограничения? Один локальный пользователь, без синхронизации; запись синхронная и рассчитана на небольшой набор данных; бюджет не гарантирует выполнение дедлайнов; журнал не сохраняется.
- Как применён SOLID? Разные ответственности у UI/domain/storage; интерфейсы Strategy/Repository/PlanReport; facade зависит от Repository, а не от файлового класса. Полного OCP нет: список разрешённых названий стратегий в Plan нужно расширять при новой стратегии.

## Небольшая модификация на защите

Добавь Shortest first:

```java
public final class ShortestStrategy implements SchedulingStrategy {
    public String name() { return "Shortest first"; }
    public java.util.List<Task> order(java.util.List<Task> tasks) {
        return tasks.stream().filter(t -> !t.done())
            .sorted(java.util.Comparator.comparingInt(Task::minutes)
                .thenComparing(Task::due).thenComparing(Task::id)).toList();
    }
}
```

Затем добавь название в разрешённый список `Plan`, пункт в JComboBox и выбор новой стратегии в `StudyWindow`. Добавь тест, где короткая задача идёт первой, и повторно запусти `build.ps1 test`. Если времени мало, более простая модификация — новый подписчик EventBus, считающий события в текущем запуске.
